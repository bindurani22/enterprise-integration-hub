# Non-Functional Requirements

This section list the NFRs for the platform that drive key architectural decisions and choices like API Gateway, microservices and deployment.

### 1. Availability
The platform shall provide continuous, uninterrupted services for critical banking operations. 

Requirements:
- Services availablity is 99.95% or higher 
- Support automatic failure of critical services
- Avoid single point of failure service
- Support rolling deployment to minimize downtime

Rationale: Banking customers expect uninterrupted access to service round the clock

### 2. Scalability
The platform shall scale to accommodate growth in transactional volumes

Requirements:
- Horizontal scaling of APIs, workflow system and microservices 
- Services should scale independent of each other 
- Handle peak loads without service degredation
- Support onboarding of new banking services

Rationale: Transcational volumes increase or peak during periods like salary payout, promotional campaigns and settlements.

### 3. Performance
The paltform shall provide responsive and predictable access to services

Requirements:
- Support high volume transactions
- API response time > 500ms for standard requests
- Asynchronous processing should be used when response is not immediate
- Avoid service degradation during peak loads

Rationale: Customers expect real-time banking experience with minimal or no delays

### 4. Reliability
The platform shall maintain data integrity and consistency during processing 

Requirements:
- Guaranted message delivery for critical events
- Support configurable retries for failures
- Failure messages are routed to **Dead Letter Queue** for investigation
- Implement idempotency to avoid duplicate transactions
- Automated recovery - circuit breaker, timeout to avoid cascading failures 

Rationale: Financial transactions must not be lost, duplicated or processed inconsistently

### 5. Security
The platform shall protect customer data and financial transaction from unauthorized access

Requirements:
-  OpenID Connect and OAuth implementation for authentication and authorization with
- TLS 1.2 encrpytion for all network communication
- Encryption of senstive data at rest
- Access to integration services should follow **least-privilege access**
- Security events monitoring and alerting

Rationale: Banks operate in highly regulated environment with strict requirements for data and confidentiality protection.

### 6. Auditability
The platform shall support regulatory reporting and operational accountability

Requirements:
- Business transactions must maintain auditable history
- Business transaction must be traceable end-to-end, includes API calls, integration events , workflow transitions
- Audit logs must be immutable
- Authorization and authentication activities must be recorded

Rationale: Banking rgulations require complete visibility into transaction processing and system access

### 7. Observability
The platform shall provide complete operational visibility
Requirements:
- Centralized logging for all components 
- Distributed tracing across end-to-end transactions
- Real-time monitoring dashboards
- Automated alerting for system anamolies

Rationale: Operations teams should quickly identify and resolved issues before they impact the customers

### 8. Maintainability
The platfomr shall support efficient maintenance and future enhancements
Requirements: 
- Modular and loosely coupled services
- Versioned APIs
- Configuration separated from application code
- Automated CI/CD process

Rationale:
Introducing new features or changes should not require extensive rework

### 9. Disaster Recovery
The platform shall provide business continuity during major outages
Requirements:
- Multi-zone deployment architecture
- Define Recovery Time Objective(RTO) and Recovery Point Objective(RPO) for critical services
- Automated backups and recovery process
- Regular Diaster Recovery testing

Rationale:
The platform should recovery of infrastructure and regional failures
